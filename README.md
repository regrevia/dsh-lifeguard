# DSH 守护 · dsh-lifeguard

开发 DSH 插件时反复把 harness 修崩。这个插件把本机真实崩溃日志沉淀成一条闭环：

```
崩溃日志（黑匣子） → 归因条目 → 精简规则（lore） → 四条用法
                                     ├─ 每次会话注入提示词（预防）
                                     ├─ 导出到 dsh-lite-memory（跨会话记忆）
                                     ├─ 装插件前静态预检（拦截）
                                     └─ 起不来时停用元凶（自愈，需手动/循环确认）
```

## 装了什么

| 能力 | 入口 |
| --- | --- |
| 规则清单只在面板和 `lifeguard_rules` 里看 | 默认不写进提示词；要恢复常驻约束，把 `promptChars` 设成 300–2000 |
| 扫描崩溃日志 | 工具 `lifeguard_scan` |
| 查规则 | 工具 `lifeguard_rules` |
| 沉淀新规则 | 工具 `lifeguard_record` |
| 装前预检 | 工具 `lifeguard_check`（包结构 / patch / 工具注册契约 / ESM 语法 + 本机规则） |
| 装之前先跟已装的比一遍 | 工具调用后被动备注（重名 / 缺依赖 / 版本 / skill 撞车 / 功能重叠），不拦安装；`config.installCheck` 默认开 |
| 运行中拦截危险改动 | 见「崩溃防护」一节；状态与拦截记录用工具 `lifeguard_guard` |
| 导出清单 | 工具 `lifeguard_export`（默认只在对话里给 markdown；`target:'memory'` 才写长期记忆 global 层） |
| 起不来时自愈 | 工具 `lifeguard_heal` / CLI `doctor` |
| 大会话转世 | 工具 `lifeguard_handoff`（读懂原会话写交接单，新会话接手，原会话归档） |
| 批量转世 | 同一个工具带 `all: true`：先列清单，确认再一个个转，跑着的跳过 |
| 查转世血缘 | 工具 `lifeguard_lineage` |
| 宿主起不来时也能用 | `node cli.mjs ...`（不依赖 DSH 进程） |

## CLI

```bash
cd ~/Desktop/DSH/dsh-lifeguard
node cli.mjs status                 # 规则/条目/已扫日志数
node cli.mjs scan                   # 扫描新日志并归因
node cli.mjs rules                  # 规则清单
node cli.mjs prompt --chars 900     # 注入的那段正文
node cli.mjs check <插件目录>        # 装机前预检，命中即 exit 1
node cli.mjs export                 # 只打印清单
node cli.mjs export --memory        # 写进长期记忆 global 层（会进召回，慎用）
node cli.mjs doctor                 # 只看计划
node cli.mjs doctor --yes           # 停用元凶（先备份，可 restore）
node cli.mjs doctor --auto          # 只在确认崩溃循环（24h 同元凶 ≥3 次）时停用
node cli.mjs restore <包名>          # 撤销停用
```

## 存储

默认 `$DSH_HOME/lifeguard/`（本机 `~/.dsh/lifeguard/`）：

- `incidents.jsonl` — 以 fingerprint 归并的崩溃条目：`occurrenceTimes` 保留每次发生的时间，`count` 是真实发生次数
- `rules.json` — 规则库
- `state.json` — 已扫日志的 mtime、停用记录

日志来源：`~/Library/Logs/DeepSeek Harness/crash-*-host.log`、`crash-*-web-boot.log`、`$DSH_HOME/logs/startup-*.log`。
所有入库文本先脱敏（`sk-…`、`Bearer …`、`apiKey|token|secret|password=`）。

## 崩溃防护（运行中拦截）

预检是装之前问一次，防护是在副作用发生之前每步都问：**这次调用会不会让正在跑的宿主起不来。**

两层接在宿主自己的执行链上：

| 层 | 宿主机制 | 管什么 |
| --- | --- | --- |
| 写前守卫 | `ctx.tools.guard()`（同步，不可被放宽） | `write` / `edit` 把**写入后的完整文本**交给规则检查；`bash` 只拦对 live 插件目录的整体删除/移动 |
| 安装前预检 | `tools/pre-execute`（异步 waterfall，`next()` 放行） | `plugin_manager` 的 `install_bundle` / `set_plugin(enabled)`：先解析候选目录，跑完整 preflight，再决定是否执行 |

live 面 = profile 目录本身 + profile 里所有插件源码（含 `link:` 的开发树，因为宿主就是通过软链加载它的）。

判据是「已经证明会让本机崩溃的形态」，不是风格问题：

- 模块顶层 `throw` / 裸 `await`（P014/P015）
- ESM 里 `require`（P016）、`__dirname`/`__filename`（P017）
- 插件 `process.exit`（P018）、接管 `SIGINT`/`SIGTERM`（P019）
- patch 重复 id（P009）、patch 引用的包没声明（P010）、包结构缺失（P001/P002/P005/P007/P008）
- 装前还有 `node --check` 的语法闸（P013）、`tools.register` 没闭合（P021）
- 配置里写明文凭据

放行：读文件、看日志、搜索、改不相关项目、改开发副本、跑测试、以及 live 插件里**正常**的改动（加函数、改文案、调参数）。宁可漏拦，也不拦正常开发——被拦的会话必须能继续改自己的代码。

拒绝时返回给**发起调用的那个会话**（不另开修复会话、不广播、不停用开发中的插件）：

```
[LIFEGUARD_BLOCKED] 本次操作未执行。

插件：dsh-inner-browser-use
位置：/…/dsh-inner-browser-use/index.js:312
规则：P018 插件调用了 process.exit
原因：插件进程里调 process.exit 会直接杀掉宿主，所有会话一起掉线
证据：process.exit(1);
风险：这一步会在 running profile 里生效，宿主激活/热重载时崩溃，当前所有会话一起掉线。
建议：改成抛给 ctx 报错或返回失败结果，让加载器决定是否停用
改好后重新提交这次写入；你仍可以继续读代码、改开发副本、跑测试。
```

工具结果就是一次普通的报错，会话照常继续 —— 修完再提交同一个调用就通过。

## 安装体检

`dsh-install-check` 已并进这个插件：`plugin_manager` 装包时先跟已经装好的比一遍，装完把「撞了什么名、缺什么依赖、版本够不够、skill 有没有撞车、和谁在做同一件事」写成一条备注，随工具结果回到会话。它只加备注，从不让安装失败；读不到目标就静默跳过。

开关：`config.installCheck`，默认开；`mode=off` 时一并关闭。三种结果写在备注里：完成未发现冲突 / 完成发现问题 / 检查未完成（25 秒预算）。

同一件事、两个名字也算重叠：两个包一个注册 `memory_save`、另一个 `memory_recall`，名字不撞，但都在做记忆。这类「功能重叠」单独一条建议（同一处界面、同一类能力），只在装/启用时给一次，`config.overlapCheck`（默认开）可单独关掉，不影响重名与依赖检查。

名字只是猜，实现才是证据：装之前还会用装前预检同一套规则读一遍候选源码，只报「一激活就可能带走宿主」的那类写法（顶层 throw / 顶层裸 await / `process.exit` / 接管退出信号 / patch 引用没声明的包……），带文件和行号与改法，最多两条。规则分两层：随包发的种子规则，加上这台机器从自己崩溃日志里学到的规则——谁的机器上学到，就守在谁的安装动作前。静态读文本，不执行、不联网；运行期才出现的竞态不在其中。开关 `config.implCheck`（默认开）。

开关：插件设置里选「开启 / 仅监测 / 关闭」三档，存进 `config.mode`；老配置里的 `guard: false`（关闭）、`monitorOnly: true`（仅监测）仍然认。仅监测用于先观察误报，只记录不拦。

状态别听它自己说：`lifeguard_guard` 按实际接上的层报 `保护中 / 仅监测 / 部分覆盖 / 检查异常 / 已关闭`，并说明哪一层没接上（例如宿主没有 tools 服务时直接报 `不可用`，不会冒充保护中）。

插件本身没被加载时没有东西能回答你 —— 这种情况不会显示成 `保护中`：宿主插件列表里该入口会标 `inactive`/`absent`，`lifeguard_guard` 工具也根本不存在。安装或升级后要重启一次宿主才会接上；改完插件源码最好先跑 `node cli.mjs check .`，语法/契约错误会让加载器直接停用入口，防护随之整层消失。

**覆盖边界**（照实写在状态里，不假装全覆盖）：bash/脚本里 `cat > file`、`run_code` 里自己 `fs.writeFile`、外部编辑器保存、宿主自身升级，都绕过工具管线，这层看不到。

## 化龙妙法：大会话转世

会话越长，恢复越贵——一个大会话恢复时要几 GB 堆，本机就是这么崩的。转世不解救旧会话，而是把活交给一个新会话：读原会话记录、写一份交接单、建新会话、把旧会话归档（不删，可取消归档回看）。

交接单默认**由模型读懂原会话再写**：给了它七节模板（目标 / 结论 / 走不通的路 / 改动 / 未完成与下一步 / 风险与注意），要判断不要复述日志，最值钱的是「走不通的路」——新会话不用把失败方案再踩一遍。转世允许比平时多花一点额度，因为丢信息的代价更高。

七条硬约束，保证转世本身不会成为新的崩溃点：

- 先量内存再读记录：读一份大会话是转世最贵的动作，堆到墙的 90% 就拒绝转世并直接说清改法，不让读记录这一步把宿主带走。
- 只调一次模型，输入有字节上限、输出有字数上限、整次调用有超时；原会话再长也只留最近的记录，但最早那条需求单独保住。
- 堆到 85% 就不调模型了，直接退回自动摘要（只摘记录，不做判断）。整理交接单不该再占一大块内存。
- 交接单先写盘、回读确认字节数，再去通知新会话：发消息成功但磁盘上没有，重启后就等于没交接。没落盘的那次转世会明说「不算数」。
- 模型报错、超时、返回空、非正常收尾，一律退回自动摘要——转世不会因为整理失败而失败，结果里会说清用的是哪种。
- 交接单末尾固定让新会话先只回「收到」，免得一转世就当场再开重活，把刚空出来的内存立刻填回去。
- 挂进工作区要回读，不能写完就当成了：`attachSession` 落盘之后，成员列表还要过一遍启动时建的 cwd 索引，索引里没有的新会话会被静默滤掉。所以挂完回读 `sessionIds`，不认就补一次索引再确认；仍然不认才在结果里说「列表里看不到它」，不假装挂上了。

会话多的时候不用一个个转：`all: true` 先列清单，默认什么都不动，只给前 5 个；确认后带 `dryRun: false` 再跑。只挑已经停下、还没归档、又不是当前会话的那些——跑着的会话转世会被腰斩，跳过不劝。一次最多 5 个（`limit` 上限 10），顺序执行不并发，每个之前先看内存，到 92% 就收手。批量默认走自动摘要：每个会话都让模型读一遍，token 和堆一起涨；想要判断力，单独给那个会话传 `sessionId`。`force` 只管单会话，批量不用它绕过运行中检查。

内存还宽裕的时候先演练：`dryRun: true` 只读一次原会话、把交接单写到 `$DSH_HOME/lifeguard/handoff/preview-<会话>.md`，不建新会话、不动原会话，可以反复跑。等真要退出时再正式转世，或者就留着这份单子手动接着干——真正的交接成本不该全部压在墙边那一分钟里。

工具结果里 `ok` 只回答一件事：交接单真的在硬盘上、回读长度也一致。写不下去时 `ok` 是 `false`、`briefPath` 不出现，正文直接回填在 `text` 里——那一次不算数，先修磁盘再退。`briefChars` 是字数，`delivered` 说明交接单到了 `message`（已投递新会话）还是 `file`（只落了盘）。演练那次 `ok` 表示「演练写盘成功」，`dryRun: true` 会一起回来。

`llm: false` 可关掉模型整理，只做自动摘要（省资源，丢判断）。原会话还在跑时拒绝转世（两个会话会同时写同一份工作，旧回合还会在归档后被腰斩）；确认它停下了，或 `force: true` 强行。内存只有重启才拿得回来：重启前新会话可能有一个未完成回合，重启后打开再发一句「继续」。血缘记在 `$DSH_HOME/lifeguard/lineage.jsonl`，改标题也不会丢，链式转世靠它串起来。

接手后如果是那种要跑上百步的长回合，最后那次模型请求可能被判超时（记录里是 `Request timed out.`）：那是单次请求的时限，不是交接单太大，也不是转世弄丢了上下文。记录、交接单、改动都在，重开新会话发一句「继续」就接着往下走。

## 宿主启动崩在 inactive context

现象：重启后界面是空的，崩溃日志里是 `DesktopHostFatalError: cannot create effect on inactive context`（`INACTIVE_EFFECT`，栈在 `cordis` 的 `Fiber._reload` 与宿主 desktop 包的插件回调上）。

成因在宿主侧：上一次宿主是崩掉的，恢复时它会把插件配置重新应用一遍，而那次配置打在一个已经失效的 cordis fiber 上。插件代码改不动这条路径，硬绕只会把问题挪到别处。

处置：⌘Q 退干净再开一次；同一个元凶 24 小时内反复出现，用 `lifeguard_heal` 停用它再起（改动前会备份，可 `doctor --restore` 撤销）。会话记录和交接单都是先落盘的，界面空那一轮不代表工作丢了。

## 底部的内存状态圈

输入框下方常驻一个 16px 的圈和占用率：平时是暗色环，越过 70% 转琥珀，85% 转红并在圈里写一个感叹号。100% 是这台机器真正会死的堆，不是 V8 名义上限：崩溃日志记下的致命堆只在它仍然贴着当前运行时的上限时才算数（同一次运行时下约 4.1 GB），换过运行时、或没有崩溃记录，就退回「当前上限 × 85%」——上限每轮采样都从 V8 现读，不写死。堆占用、堆上限、进程 RSS 是三个不同的数，圈里比的是堆占用对墙。

越过 100% 时环已经满了，数字照样往上写（`103%`），状态行下面多一句「注意随时可能崩溃」——那不再是估计，是这台机器上死过一次的高度。平时不写这个数，免得把「还有多少余量」误读成「离死还有多远」。反过来说 99% 也不保证下一秒没事：`heapUsed` 是上一次 GC 之后的值，一次大分配就可能在你看到 90% 之前撞死，所以闸门在 85%（`high`）就开始压重操作，95%（`stop`）只放行小步写入。

每个用户按自己的日志校准：有崩溃记录就用自己最高的一次致命堆当满阈值，没有就先按上限 × 85% 顶替，等真的崩过一次，下一次采样会自动换成他自己的数字——不需要谁去调参数。圈和状态行共用同一个 crashMB，不会出现「圈按崩溃点、文字按上限」这种两把尺子；平时状态行只报已用和上限，越过 100% 才加一句提醒。

没有崩溃记录的新机器不会瞎猜：先按 `上限 × 85%` 顶替（状态里标 `basis: margin`），等崩过一次、日志里出现第一条 `heap NNNN MB`，下一次读数就换成本机自己的数字，不需要改任何配置。这个数会跟着日志走——启动时读一次，之后只在文件变动或满一分钟时重读，最多一分钟跟上新记录；换过运行时、崩溃点不再贴近当前上限时自动作废，退回 `上限 × 85%`。

读不到数据时它不消失，淡成 `内存 –`：会消失的指示器分不出「内存没事」和「指示器坏了」。路由挂没挂上，用 `lifeguard_guard` 看那行自检。读数只在界面用，不进提示词。

开关：`config.healthBadge`（默认开）。

## 临时会话快照

崩溃排查会把会话快照复制到系统临时目录，一份几十到几百 MB，跑几次就能吃掉几十 GB（本机真到过 58 GB，磁盘只剩 42 GB）。现在启动时清一次、之后每 30 分钟清一次：删掉超过 6 小时的和超预算的，从最老的删起，刚建出来十分钟内的不删。默认预算 5 GB，`config.tmpBudgetMB` 改上限（256–102400），`config.tmpTtlHours` 改保留期（1–168 小时）。只认自己造的 `lifeguard-sessions-*`、`crash-lore-sessions-*` 等前缀，别的文件一个不碰。

## 安全边界

- 只读日志，不改 DSH 安装目录；写盘只限 `$DSH_HOME/lifeguard/`。
- `doctor` 只改 profile 的 `package.json` 与 `cordis.patch.yml` 里对应那一行，改前 `*.bak-<ts>` 备份；解析失败就放弃，不留半写状态。
- 停用可撤销：`restore`，或手动把 `.bak-<ts>` 拷回。
- 静态守卫只在低误报写法上开（如 `process.exit(`、模块顶层 `throw`、真实脱离 ESM 的 `require`）；`createRequire()` 与函数体里被 try/catch 兜住的 `throw` 不报。

## 自愈怎么做到的

崩溃杀死上一个宿主进程，日志留在磁盘上。下一次启动时本插件先跑一次扫描，把新日志变成条目并归因到元凶插件——**启动阶段只记录，不自动改 profile**。

真起不来时用 `node cli.mjs doctor` 看计划、`--yes` 执行；`--auto` 只在确认崩溃循环时执行。停用前先备份 `package.json` / `cordis.patch.yml`，中途写失败会回滚已改文件，`restore <包名>` 可撤销（只注释过 patch 的隔离也能恢复）。

同一指纹每次发生都会记进 `occurrenceTimes`，`--auto` 按 24 小时窗口内的真实事件数判断「一次性」还是「崩溃循环」，不拿历史累计次数充数。

所以「自我阻止」不是拦截每一次崩溃，而是**同一形态的崩溃不会连续发生第二次**——代价是有一次手动执行的 doctor/heal。
